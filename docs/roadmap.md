# 重构路线图

状态：目标路线。本文定义依赖和阶段关卡；实时进展只在各阶段执行计划及 [交接入口](handoff.md) 维护。

## 总体顺序

```text
M0 接管文档
  → M1 工程基线
  → M2 渲染对照验证与定案
  → M3 科学核心
  → M4 格式、编辑事务与计算运行时
  → M5 viewer 显示与交互
  → M6 demo、分发验收和旧实现清理
```

允许阶段内部按独立文件边界并行。后续阶段可以做不改变交付边界的资料整理，但不能跳过其入口条件或预先宣称完成。渲染引擎选择不改变领域与格式层对引擎独立的要求。

## 关键关卡

1. **事实与目标分离**：M0 不安装依赖、不修改业务代码；静态问题不能写成已运行复现。
2. **工程可验证**：M1 修复依赖归类和锁文件并记录原始失败，不通过关闭严格检查建立“绿色”基线。临时沿用旧代码验证搬迁，不要求增加兼容公开 API。
3. **选型先取证**：M2 在同一硬件、浏览器、场景和画质下对照。候选未满足门槛时先定位和复测，不能为了选定赢家删除正式需求。最终只保留一个正式渲染实现。
4. **科学结果有参考**：M3 通过解析解及独立参考建立可信模型；静态表的数量和旧测试结果都不是数据正确性的证明。
5. **并发与编辑闭环**：M4 在没有 viewer 的测试中证明事务、撤销、取消、过期结果隔离和错误恢复；M5 再证明其浏览器集成。
6. **真实消费者验收**：M6 安装实际打包产物，不通过源码别名绕过 `exports`、声明或 Worker 加载。完成后再清除失去用途的历史实现和临时选型依赖。

## 计划补全规则

M1、M2 在 M0 时提供直接执行步骤。M3–M6 已有明确输入、交付和验收；执行前将前置阶段产出的确切类型、引擎版本及验证路径补入对应计划。引擎专属细节必须引用 M2 的 Accepted ADR，不进行第二次无依据选型。

范围、科学约定或关卡改变时，更新相关规范和 ADR，并说明改变理由。不要仅修改任务清单而保留互相矛盾的目标描述。
