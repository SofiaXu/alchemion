# ADR 0002：正式渲染后端选型

日期：2026-10-29。状态：**Proposed**。负责阶段：M2。当前赢家：**未确定**。本文件没有基准结果，任何候选都尚未通过项目验证。

## 背景与约束

[ADR 0001](0001-project-foundation.md) 要求浏览器 SDK、现代桌面 WebGL2 和扩胞后 10,000 个原子显示实例。旧实现使用 Babylon.js 不构成保留该引擎的兼容约束。Three.js 与 Babylon.js 都有实例化能力；项目的更新、拾取、销毁、Worker 接入和包体积仍需在同条件原型验证。

最终只维护一个正式后端。M2 的两份最小原型用于比较，禁止提前扩展成两套完整 viewer、编辑系统或通用引擎插件框架。领域与格式保持引擎无关，无论哪一候选获选。

## 候选与证据边界

| 候选       | 可用于原型的官方能力资料                                                                                                   | 本项目尚待证明                                               |
| ---------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| Three.js   | [InstancedMesh](https://threejs.org/docs/pages/InstancedMesh.html) 的实例变换/颜色、实例拾取与更新能力。                   | 固定场景下的交互、增量更新、清理、Worker 边界与分发成本。    |
| Babylon.js | [Thin instances](https://doc.babylonjs.com/features/featuresDeepDive/mesh/copies/thinInstances) 的大量实例与缓冲更新能力。 | 同等画质下的拾取 ID、局部更新、清理、Worker 边界与分发成本。 |

官方文档证明 API 能力存在，不是本项目性能证据。M2 开始时核对当前官方文档与实际锁定版本，记录两个候选的精确版本及构建参数，不写“最新版”作为可复现环境。

## 固定比较口径

两个候选使用同一个已准备好的 `RenderSnapshot`、同一套相机/光照/颜色/背景/球与棍拓扑、相同抗锯齿和透明度设置、1920×1080 CSS 画布与 DPR 1。场景为 10,000 个原子实例及 20,000 条键；空间填充和球棍两种模式都执行完整性能与资源验收。空间填充仍接收同一含键快照，但按该模式不绘制键。

同一设备和浏览器上每候选的每种模式运行三轮独立测试并交替顺序，记录设备、GPU、驱动、OS、浏览器、精确版本、WebGL renderer、供电模式及全部参数。固定夹具、脚本、采样方式和限制见 [M2 计划](../plans/m2-renderer-selection.md) 与 [质量规范](../quality.md)。不比较来自不同设备或不同画质的数字。

硬门槛如下，均为待实测目标：

- 从准备好的 RenderSnapshot 交给 renderer 到首次完整帧 ≤5 秒；文件/网络/科学计算另外记录。
- 60 秒持续交互期间 median FPS ≥30。
- 点击拾取结果 p95 ≤100 ms，且实例 ID 与源 ID 正确。
- 每次更新 100 个原子及受影响键的显示提交 p95 ≤100 ms。
- 20 轮创建/显示/销毁后，自有 GPU、Worker、RAF、观察器/监听资源计数归零且无累积；JS heap 只记录趋势，不要求精确归零。
- Worker 可通过相同引擎无关快照接入；取消/过期结果与 clear/dispose 不能生成错误帧；普通 ESM 消费者可以加载构建产物。实现不依赖私有 API、维护引擎补丁或修改全局引擎状态。

## 有限决策规则

1. 两种模式的每轮必须满足全部硬门槛。任一功能或生命周期硬门槛失败的候选不入选；单一候选通过则选择它。
2. 两者都通过时，先比较所有模式/各三轮中最差的 `max(拾取 p95, 100 原子更新 p95)`；以较高值为分母，较低者领先至少 10% 时选它。
3. 延迟差不足 10% 时比较同构建参数下包含引擎的 viewer 入口 gzip 体积，较小者胜出；以较大体积为分母，相差不超过 1% 视为平手，以 Three.js 为事先声明的最终平手规则。该规则只在同等达标且前述指标无法区分时使用，不是提前选定引擎。候选专属代码量、清理复杂度和 API 使用情况作为解释性证据，不把 LOC 当质量分数。
4. 两者都失败时，每个失败候选最多进行一轮有证据的针对性修复，并完整重跑。修复后仍无达标候选，M2 停在未通过状态，写明失败指标和可复现证据；需要修订预算或候选范围时先更新相关决定，不能无限调参或跳过关卡。

不得只凭包体积、旧代码熟悉程度或纸面 API 比较决定赢家。体积结果至少包括原始、minified、gzip 字节及 shared/core 的归属说明，不将 gzip 数值当运行内存。

## 接受条件与定案产物

M2 只有在提交可重跑夹具/命令、每种模式各三轮原始数据、画质截图、资源计数、Worker/拾取正确性结果和明确选择理由后，才能将本 ADR 改为 Accepted，并写入获选引擎与精确版本。报告目标位置为 `docs/evidence/m2-renderer-selection.md`，当前尚未生成，不作已存在文件链接。

定案同一变更中更新架构、M5 的引擎专属实现步骤和打包约束，移除失败候选的运行依赖与临时原型；保留报告、夹具说明和必要的比较记录，正式测试只维护获选后端。若原型有可复用共享工具，将其保留为测试资产，不保留第二条正式渲染路径。
